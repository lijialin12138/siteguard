## 1. 总体评价

**结论：架构清晰、职责单一、核心方法论（控误报）已扎实落地，达到参赛演示与答辩要求。**

系统采用严格的分层架构，数据从「发现」到「呈现」单向流动，每一层只做一件事：

```
scanner.py  ──发现──▶  report(dict)  ──▶  ai.py  ──分析──▶  诊断结论
                                   │                        │
                          service.py ──编排──▶ 落库 / 查询     │
                                   │                        │
                              db.py ──持久化──▶  SQLite       │
                                   │                        │
                            main.py ──API──▶  前端             │
                            scheduler.py ──定时触发──▶  run_scan_all
```

贯穿全系统的「数据契约」是 `scanner.scan_site()` 返回的 `report` 字典（字段在 `scan_site` 的 docstring 里有完整定义）。存储、AI、前端三处共用它——这是设计上的枢纽，也是改动时的高风险点（改它之前必须通知另外两条线）。

## 2. 各模块审查

### 2.1 `scanner.py` —— 巡检引擎（⭐ 核心竞争力所在）

| 维度 | 评价 |
|---|---|
| 职责单一 | ✅ 只做「发现问题」，分析原因交给 `ai.py`，注释里明确写死这条边界 |
| **控误报方法论** | ✅ **全场最佳设计**。链接探测分三档：`broken`（404/410 确认失效）/ `server_error`（5xx 瞬时）/ `unverified`（连不上、被拒、被限流，**不当失效**） |
| 二次复核 | ✅ HEAD 失败或返回 4xx/5xx 时强制用 GET 再确认一次，规避「微信公众号等站点对 HEAD 直接断连」导致的死链误报 |
| 误判红线 | ✅ `DEFINITIVE_GONE = {404, 410}` 只把这两个状态码判失效；**403/429 明确归入待确认**，注释用实测案例说明了为什么（某高校官网 6 个子站被限流返回 403，几分钟复测全恢复 200） |
| 阈值可配置 | ✅ `RESP_VERY_SLOW_MS / RESP_SLOW_MS / SSL_WARN_DAYS` 经 `config._get_int()` 读取，团队已据此做过练习 |
| 并发与容错 | ✅ `Semaphore(MAX_CONCURRENCY)` + `asyncio.gather(return_exceptions=True)`，单链接异常不拖垮整体 |

**答辩可讲**：巡检类工具的核心竞争力不是「发现多少问题」，而是「误报率」。把「无法验证」说成「死链」，会让客户去修没坏的东西，报告直接失去可信度。本项目从状态码分档、HEAD/GET 二次复核、误报红线三道关卡把误报压到最低，这是和其它「死链检查器」的本质区别。

### 2.2 `ai.py` —— AI 诊断层

| 维度 | 评价 |
|---|---|
| 华为技术接入 | ✅ 用 OpenAI 官方 SDK 直连华为云 MaaS（`AsyncOpenAI(base_url=MAAS_BASE_URL)`），base_url 指向 `https://api.modelarts-maas.com/openai/v1`，接口完全兼容 |
| 约束一致性 | ✅ `SYSTEM_PROMPT` 把「三档链接严格不同、unverified 不当死链」写进系统提示词，**与 scanner 的分档口径完全一致**，避免 AI 自作主张把 403 当死链 |
| 模式兜底 | ✅ `MAAS_MODE=auto`：配了真实 Key 走真模型，没配走内置 mock 诊断（`_mock_diagnose` 读真实 issues、输出结构与真模型一致），开发期不断链 |
| 输出容错 | ✅ `_extract_json` 处理 ` ```json ` 包裹与前后缀；`_slim_report` 只送关键字段降低 token 消耗与被干扰概率 |
| 真实调用验证 | ✅ 实测 `ai.diagnose()` 返回 `_meta={model: deepseek-v4-flash, total_tokens: 1487}`，确认为真模型，且输出遵守了三档约束 |

### 2.3 `service.py` —— 业务编排层

| 维度 | 评价 |
|---|---|
| 路径统一 | ✅ `run_scan_for_site` 被手动 API 和定时任务共用，避免两处各写一遍导致行为漂移 |
| 隔离性 | ✅ `run_scan_all` 对单站点异常 `try/except`，一个站点失败不影响其他站点 |
| 查询支撑 | ✅ `latest_scan_per_site` 给 Dashboard 用，刻意把「确认失效数 / 5xx 数 / 无法验证数」三档分开展现（注释说明混在一起会吓到用户、降低报告可信度） |
| 诊断落库 | ✅ `save_diagnosis` / `get_latest_diagnosis` 存模型名与完整结论 JSON，可追溯 |

### 2.4 `db.py` —— 数据访问层

| 维度 | 评价 |
|---|---|
| **可演进性** | ✅ 所有 SQL 集中在此文件，注释明说「迁移华为云 RDS 只需改这一个文件」——这正是为参赛「采用华为云技术」做好的迁移接口 |
| 防注入 | ✅ 全部用 `?` 参数化占位，无字符串拼接 SQL |
| 数据完整性 | ✅ 外键 `ON DELETE CASCADE`（站点删 → 巡检/问题/诊断级联清），索引覆盖 `site_id`、`scan_id` 查询 |
| 现场保留 | ✅ `scans.raw_json` 存完整 report，便于事后复盘而不仅是聚合结果 |

### 2.5 `main.py` —— API 入口

| 维度 | 评价 |
|---|---|
| 生命周期 | ✅ `lifespan` 统一管理 `init_db()` + `start_scheduler()`，启动幂等、关闭优雅 |
| 异常处理 | ✅ 分类型映射：`ValueError→404`、`UNIQUE→409`、MaaS 未配 `→400`、调用异常 `→502`，前端能精确区分 |
| 状态可观测 | ✅ `/api/status` 暴露 `maas_configured / mock_active / scheduler`，`/api/status/maas-ping` 提供一键连通性自检 |

### 2.6 `scheduler.py` —— 定时调度

| 维度 | 评价 |
|---|---|
| 轻量 | ✅ `AsyncIOScheduler` 跑在 FastAPI 事件循环内，不引入 Redis / Celery，符合「一周出原型」目标 |
| 防重叠 | ✅ `max_instances=1 + coalesce=True`，错过触发时间不会堆出多份并发巡检 |
| 手动触发 | ✅ `trigger_now()` 支持立即跑一轮，演示时不必干等 |

## 3. 亮点总结（答辩重点）

1. **控误报方法论**是产品级亮点，不是玩具脚本。三档分桶 + HEAD/GET 二次复核 + 误报红线，构成可信报告的基石。
2. **真实接入华为云 MaaS**，已端到端验证通过（`deepseek-v4-flash`，按量计费，成本可忽略），满足赛题「采用华为技术」硬要求。
3. **架构可演进**：SQLite → 华为云 RDS 的迁移路径已预留（SQL 全集中在 `db.py`）；AI 接入层与具体模型解耦（`MAAS_MODEL` 可换）。
4. **开发不断链**：`MAAS_MODE=auto` + 内置 mock 诊断，没有真实 Key 也能完整跑通「巡检 → 诊断」链路，演示零成本。

## 4. 风险与改进建议

按优先级排列，前两条建议在大赛初赛前处理：

| 优先级 | 风险点 | 建议 |
|---|---|---|
| 🔴 高 | **真实模型输出无 Schema 强校验**。`_extract_json` 只做 JSON 解析，模型偶尔漏字段（如缺 `actions`）时下游会 KeyError。 | 用 `pydantic` 对诊断结论做模型校验 + 缺字段补默认值，保证前端稳定 |
| 🔴 高 | **API 无鉴权**。`main.py` 所有接口裸奔，本地 demo 无妨，一旦部署公网任何人可增删站点、触发巡检、消耗 MaaS 额度。 | 部署前加一层简单鉴权（如固定 token / 华为云 APIG 网关），并在 `ONBOARDING` 注明 |
| 🟡 中 | **定时任务单点**。APScheduler 内存存储，进程重启即丢；多实例部署会重复触发。 | 初赛阶段可接受；决赛若多实例，迁到华为云定时器或加分布式锁 |
| 🟡 中 | **单页链接上限**。`MAX_LINKS_PER_PAGE` 限制探测规模，大型站点可能漏检内链。 | 对大赛演示站点足够；若需覆盖大站，可改为分页/多线程深扫并加总预算上限 |
| 🟢 低 | **SSL 检查走同步 executor**（`run_in_executor`），高并发站点多时略成瓶颈。 | 可用 `ssl` 异步库或批量探测优化，当前规模无感知 |
| 🟢 低 | **`scans` 表只存 `broken_links` 数量**，5xx / unverified 数需从 `raw_json` 现解。 | `latest_scan_per_site` 已在 service 层补算，代价是每行多一次 JSON 解析；量大时可在 scans 表加冗余列 |

# SiteGuard 修复闭环演示 · 靶站与答辩脚本

> 用途：在比赛答辩 / 队友联调时，安全、可控、可复现地演示
> 「扫描 → 诊断 → 出补丁 → 手动修复 → 复扫对比」完整闭环。
> 适用对象：队长（霖）、小格、小甘。

---

## 0. 为什么用靶站（合规边界，评委必问）

**铁律：第三方站点（含学校官网）只做「只读巡检 + 诊断 + 出补丁」，补丁必须标注
"需站点所有者授权后应用"，我们绝不自行修改。**
修复闭环的"应用补丁 → 复扫改善"只在**自己搭建的靶站**上演示。

- 靶站位于 `siteguard/demo-target/`，只绑 `127.0.0.1`，不对外、不属于任何真实网站，可随意修改，零合规风险。
- 学校官网（`www.ncpu.edu.cn`）我们只做"发现问题"那一截（只读巡检+诊断+出补丁），
  截图留作证据；"动手修复"那截用靶站，避免未授权改动他人信息系统
  （涉《网络安全法》第 27 条、《刑法》第 285/286 条）。
- 这条边界本身也是加分项：**我们知道产品的权力边界在哪**——SiteGuard 的定位是
  "给出诊断与修复建议，执行权永远在客户手里"。

## 1. 准备工作（演示前一次）

**① 启动靶站**（cmd，在 `siteguard` 目录下）：
```bat
.venv\Scripts\python.exe demo-target/server.py
```
出现 `演示靶站已启动 http://127.0.0.1:8001/` 即成功。

**② 启动 SiteGuard 主服务**（真模型模式，在 `siteguard` 目录下）：
```bat
MAAS_MODE=off .venv\Scripts\python.exe -m uvicorn app.main:app --reload
```
浏览器开 `http://127.0.0.1:8000/`。

**③ 若扫描 `127.0.0.1` 卡住/失败**（机器有代理时）：PowerShell 先设：
```powershell
$env:NO_PROXY="127.0.0.1,localhost"
```
再启动上面两个服务。

## 2. 现场演示步骤（照着点）

| 步 | 操作 | 期望看到 |
|---|---|---|
| 1 | 添加站点 → `http://127.0.0.1:8001/` | 站点入库 |
| 2 | 点「扫描」 | 报告：200 / 响应快 / SSL 不适用(http) / 失效 1 / 5xx 1 |
| 3 | 点「诊断」 | 走华为云 MaaS 真模型 `deepseek-v4-flash`，真实消耗 token |
| 4 | 进「修复」面板 → 查看补丁 | 调 `GET /api/scans/{id}/patch`，出现**多段可落地补丁**，每段一键复制 |
| 5 | **手动修复** `demo-target/index.html`（见第 3 节） | 改的是你自己文件，无合规风险 |
| 6 | 点「复扫」→ 看前后对比 | 对应问题变成「已修复」 |

> 演示要点：复扫对比里，如果某个链接只是 403/429 限流（误报），会标「待确认」
> 而**不会谎报"已修复"**——这正是我们误报治理的底线，演示时可特意点出。

## 3. 靶站内置缺陷 → 对应补丁

`demo-target/index.html` / `server.py` 故意埋了 4 类缺陷，修复方式如下：

| 缺陷 | 扫描判定 | 诊断出的补丁（patch 字段） | 手动修复做法 |
|---|---|---|---|
| 首页无 `<meta name="description">` | P3 `seo` | 补一段 `<meta name="description" content="...">` | 在 `<head>` 里加上这行 |
| 1 张 `<img>` 无 `alt` | P3 `accessibility` | 给 `<img>` 加 `alt="..."` | 给 `<img>` 补 `alt` 属性 |
| 链接 `/missing-page.html` 不存在 | P1 `broken_link`（404 确认失效） | 修复/删除该死链的建议 | 删掉该 `<a>`，或新建真实页面 |
| 接口 `/boom` 返回 500 | P2 `link_server_error`（5xx） | **只读复核命令**（`curl -sI`），不给删除 | 删掉该 `<a>`，或修 `server.py` 的 `_boom` |

> 注意：`link_server_error` 的补丁是"用 curl 复核"，**不是删除命令**——
> 我们的产品铁律是：对"无法确认/服务端异常"的链接只给复核建议，绝不教唆删文件。

## 4. 答辩解说词（评委视角）

**Q：你们怎么控制误报？**
> 链接探测分三档：404/410 才算确认失效（P1），5xx 是服务端异常（P2），
> 连不上/被限流（403/429）只标"待确认"，不当死链。HEAD 失败一律用 GET 二次复核。
> 我们比的是"误报率"而不是"发现多少问题"——把"无法验证"说成"死链"会让报告失去可信度。

**Q：你们真用了华为云吗？**
> 真用了。诊断走华为云 MaaS（贵阳一）的 `deepseek-v4-flash`，真模型、真实计费，
> 不是内置 mock。证据见 `docs/真模型验收样例.md`（含 token 消耗与模型名，已脱敏）。

**Q：闭环安全吗？会不会乱改客户网站？**
> 安全。产品明确不自动修改任何远程网站，补丁由客户在自己环境应用。
> 演示用的"修复→复扫"是在我们自建的本地靶站上跑的；
> 对真实站点（如学校官网）只做只读巡检，补丁需授权后才由对方执行。
> 这条边界是产品的设计原则，不是临时补救。

**Q：补丁靠不靠谱？会不会编造？**
> 提示词硬约束：只针对报告里真实存在的问题给补丁，禁止编造；
> `link_unverified` 场景绝不给删除命令。后端还有 `_validate_patches` 兜底校验
> （空 code / category 越界 / 含删除命令一律拦截并告警）。

## 5. 已验证事实（无需重新跑）

用真实扫描引擎对 `http://127.0.0.1:8001/` 实测，稳定产出四类缺陷：

```
[P1] broken_link:     发现 1 个失效链接（HTTP 404/410，资源确实不存在）
[P2] link_server_error: 1 个链接返回服务端错误（5xx）
[P3] seo:            缺少 meta description，影响搜索收录
[P3] accessibility:  1 张图片缺少 alt 描述
```

路由实测：`/`→200、`/about.html`→200（健康对照）、`/missing-page.html`→404、`/boom`→500。

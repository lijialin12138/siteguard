# AI诊断知识库

> 来源：app/ai.py 内 _MOCK_KNOWLEDGE 模拟知识库 & SYSTEM_PROMPT

## 故障对照表

| 问题类别 | 根因 | 处置动作 | 操作步骤 | 修复片段 |
|---|---|---|---|---|
| availability | 站点在超时时间内完全没有响应。常见原因是 Web 服务进程已退出、DNS 解析异常，或云上安全组 / 防火墙拦掉了 443 端口的入站流量。 | 恢复站点可用性 | 登录服务器执行 systemctl status nginx 确认进程状态；在服务器本机执行 curl -I http://127.0.0.1/ 区分服务挂了还是网络不通；再检查云主机安全组的 80/443 入方向规则是否放行。 | `systemctl status nginx`、`curl -I http://127.0.0.1/`、`curl -I https://你的域名` |
| server_error | 服务端返回 5xx，说明请求已经到达后端但处理过程抛出了异常，通常是应用报错、上游依赖不可用，或 PHP/Java 进程资源耗尽。 | 定位后端异常并恢复服务 | 查 Nginx 与应用错误日志，重点看 5xx 前后 1 分钟内的堆栈；同时确认数据库连接数是否打满、磁盘是否写满。 | `tail -n 200 /var/log/nginx/error.log`、`df -h`、`free -m` |
| client_error | 页面返回 4xx，多数是资源路径被改动后没做重定向，或权限配置把正常访客也挡在了外面。 | 修正失效路径或权限规则 | 在浏览器开发者工具 Network 面板确认具体 URL 返回 4xx；如果页面被改名，加 301 永久重定向；如果是 403，检查目录权限与 Nginx deny 规则。 | `location = /old-page.html { return 301 /new-page.html; }` |
| redirect | 存在 HTTP 跳转，单次跳转本身无害，但如果 HTTP→HTTPS 与 www→裸域各跳一次，会增加移动端首屏时间，也可能分散搜索权重。 | 合并跳转链路为一跳 | 先用 curl -I 观察完整跳转链，再把 Nginx 里的 HTTP 与 www 规则合并，直接 301 到最终主域名。 | `server { listen 80; server_name 你的域名 www.你的域名; return 301 https://你的域名$request_uri; }` |
| performance | 首页响应耗时偏高。后端首字节时间长通常是数据库慢查询或未加缓存；如果 TTFB 正常但总时间长，则是图片、JS 体积过大且未启用压缩缓存。 | 先压低首字节时间，再做静态资源优化 | 用 curl 测 TTFB，超过 0.6s 优先加 Redis 缓存和慢查询索引；TTFB 正常则开启 Nginx gzip 并为静态资源设置长缓存。 | 开启 gzip，配置 `expires 30d` 和 `Cache-Control "public"` |
| ssl | HTTPS 证书临近到期。企业站点最典型的事故就是证书过期，一旦过期浏览器会直接弹出安全警告拦截访问。 | 完成证书续期并配置自动续期 | 登录域名服务商或 CA 控制台确认证书到期日，完成续期与重新部署；同时用 certbot 配置定时自动续期。 | `sudo certbot renew --dry-run`、`sudo systemctl enable --now certbot.timer`、`sudo nginx -t && sudo systemctl reload nginx` |
| broken_link | 存在指向 404/410 的站内链接，对方服务器明确回应该资源不存在，通常是页面改版或文章下线后忘记同步更新链接。 | 清理死链并补上重定向 | 导出全部 4xx 链接清单，逐条判断：有效内容补 301 到新地址，已下线内容从页面摘除；CMS 增加发布前链接检查。 | `wget --spider -r -nd -nv -o spider.log https://你的域名`、`grep -E " 40[0-9] | 50[0-9] " spider.log` |
| link_server_error | 被链接页面返回 5xx，说明请求到达对方服务器但处理失败。这类错误往往是瞬时故障，不能直接判定链接失效。 | 复测确认后再决定是否整改 | 对这批链接间隔一段时间复测 2–3 次；若持续 5xx，再联系对方负责人或从本页面暂时摘除。 | `curl -o /dev/null -s -w "%{http_code}\n" https://可疑链接` |
| link_unverified | 巡检时没能拿到有效响应，常见原因是反爬拦截、要求登录、高频请求限流或网络临时不通。它们不等于失效链接。 | 人工抽查确认，不要直接删除 | 从清单里随机挑几条在浏览器打开；能正常访问说明是反爬拦截，应从巡检结果剔除；真打不开再跟进。 | 用浏览器抽查 + `curl -A "Mozilla/5.0"` 复测 |
| seo | 页面缺少 title / meta description / H1 等基础标签，会影响搜索引擎收录质量与点击率。 | 补齐页面基础 SEO 标签 | 为每个页面补独一无二的 title 和 description，并保证每页有且仅有一个 H1。 | `<title>标题</title>`、`<meta name="description" content="描述">`、`<h1>页面主标题</h1>` |
| accessibility | 部分内容图片缺少 alt 文本，视障用户无法通过读屏软件获知图片信息。 | 为内容图片补充 alt 描述 | 承载信息的图片写说明性 alt；纯装饰图片写空 `alt=""`，让读屏软件跳过。 | `<img src="banner.jpg" alt="说明">`、`<img src="divider.png" alt="">` |

## SYSTEM_PROMPT原文

```text
你是一名资深的企业级网站运维工程师（SRE），擅长从监控数据中快速定位故障根因。
你会收到一份由自动化巡检程序生成的「网站体检报告」JSON，里面可能包含：
站点地址、HTTP 状态码、响应耗时、SSL 证书剩余天数、
页面基础信息（标题/描述/H1 数量/图片 alt 缺失数）、链接异常清单，
以及程序依据规则初步标记的问题清单 issues。
关于链接异常，报告里会分三类给出，含义严格不同，不要混用：
- broken_link_count：对方明确返回 404/410 的失效链接，这才是真正需要修的死链；
- link_server_error_count：返回 5xx 的链接，可能是服务端瞬时故障，未必是链接本身的问题；
- link_unverified_count：连不上、被反爬拦截或被限流而无法验证的链接。
不要在结论里把它们说成死链，只能提示人工确认或稍后复测。

你的任务是分析报告并给出诊断结论。
严格遵守以下输出要求：
1. 只输出一个 JSON 对象；
2. JSON 结构必须包含 summary、severity、root_causes、actions、patch；
3. root_causes 和 actions 按重要性从高到低排序，最多各 3 条；
4. 严禁编造报告中不存在的数据；
5. 全部用中文回答；
6. actions 里的 how 要具体到可操作。
